## 1. 테스트 목적

#### 설계

- 로그인이 유지되는 사용자가 이 서비스를 통해 위치 알림을 받을 때의 최소 흐름은 다음과 같이 설계했습니다.
    1. 친구 목록 조회
    2. 한 대상에게 도착 알림 요청
    3. 알림 수신함 갱신

    - 추가적으로 다음과 같은 요청이 발생할 수 있음
        - 내 정보 조회
        - 받은 친구 요청 조회
        - 알림 수신함 조회

(현재는 사용자가 없기에 설계를 기준으로 평균 요청 수를 가정했습니다.**)**

여기에 `내 정보`, `받은 친구 요청`, 추가 `알림 수신함 조회`가 매번 전부 호출되지는 않는다고 보면, 평균적으로 선택 요청이 약 2회 추가된다고 가정하면 평균 5회가 발생합니다.

#### 필요하다고 판단한 이유

서비스 특성상 위치가 바뀌는 순간에만 요청이 발생합니다. 이 특성 때문에 전체 사용자가 하루 동안 고르게 요청을 보내기보다는, 퇴근 및 귀가 시간대인 18시~20시에 사용이 집중될 것으로 예상했습니다.

그렇기 때문에, 특정 요청이 몰리게 되는 경우에도 현재의 서버 구성으로 안정적으로 처리하는 구간이 어디까지인가를 판단할 수 있어야 차후에 미리 문제를 해결할 수 있다고 판단하여 부하테스트를 진행했습니다.

## 2. 부하 테스트 환경

#### 별도의 환경 구축 이휴

- 운영 환경에 부하를 걸어 서비스의 운영 불가 상태를 가지는 것은 위험하다고 판단했습니다.
- 로컬 PC에서 앱을 띄워 측정하게 될 경우, 실제 운영 환경과의 일치율이 달라 의미가 없다고 판단했습니다.
    - 높은 사양의 로컬 PC
    - 같은 PC 내부에 존재하는 DB로 인한 DB IO 시간 감소

#### 채택한 원칙

- 운영 서버와 같은 AWS 리전, 사양, 같은 이미지를 사용한다.
- 운영과 분리된 별도의 스택, VPC 를 사용한다
- 사용 후 인프라 자원 반납
- 부하 발생은 로컬 PC에서 진행한다.
    - 비용 고려.

템플릿 : `load-test-aws-setup.yaml`

#### 구성

```
로컬 PC
  └─ k6 ── HTTP/HTTPS ──▶ 애플리케이션 EC2  (t3.small)
                            ├─ Spring Boot
                            ├─ nginx
                            └─ Alloy ──────▶ 모니터링 EC2  (t3.small)
                                              ├─ Prometheus
                                              ├─ Loki
                                              ├─ Tempo
                                              └─ Grafana
                                  │
                                  ▼
                            데이터베이스 EC2  (t3.small)
                              └─ MySQL 8.0 (OS에 직접 설치)
```

- **서버**
    - 운영
        - Amazon Linux 2023
        - EC2 `t3.small`
        - 3개의 컨테이너 실행
            - Spring Boot
            - nginx
            - Alloy
    - 부하 테스트
        - Amazon Linux 2023
        - EC2 `t3.small`
        - 3개의 컨테이너 실행
            - Spring Boot
            - nginx
            - Alloy
- **DB**
    - 운영
        - 가비아 DB 사용
        - 최대 커넥션 수: `30`
    - 부하 테스트
        - 별도의 EC2에 MySQL 구성
        - `max_connections=30`
- **모니터링**
    - 운영
        - Grafana Cloud 사용
    - 부하 테스트
        - 별도의 EC2 `t3.small` 사용
        - Grafana
        - Prometheus
        - Loki
        - Tempo
    - 차이
        - 부하 테스트에서 대량으로 발생하는 메트릭·로그·트레이스를 운영 Grafana Cloud와 분리
        - SaaS 수집 한도와 비용이 테스트 결과에 영향을 주지 않도록 별도 환경 구성
- **nginx**
    - 운영
        - `limit_req`: IP당 `10r/s`, 전체 `100r/s`
        - `limit_conn`: `20`
    - 부하 테스트
        - 속도 제한 제거
    - 차이
        - 운영 환경의 속도 제한을 유지하면 애플리케이션보다 nginx에서 먼저 요청이 제한될 수 있음
        - 서버 자체의 처리 한계를 측정하기 위해 부하 테스트에서는 제한을 제거
- **TLS / 도메인**
    - 운영
        - 실제 도메인 사용
        - Let’s Encrypt 인증서 적용
    - 부하 테스트
        - Self-signed 인증서 사용
        - `server_name _`
- **외부 공급사**
    - 운영
        - Firebase
        - Solapi
    - 부하 테스트
        - `loadtest` 프로필의 가짜 Adapter 사용
        - 기본 설정
            - `LOADTEST_PROVIDER_DELAY_MS=0`
            - `LOADTEST_PROVIDER_FAILURE_RATE=0.0`
    - 차이
        - 외부 공급사의 속도 제한이나 비용이 서버 자체의 처리 한계 측정에 영향을 주지 않도록 가짜 Adapter로 대체
        - 필요할 경우 지연과 실패도 재현 가능
            - `LOADTEST_PROVIDER_DELAY_MS`
                - 공급사 호출 지연 시간(ms)
            - `LOADTEST_PROVIDER_FAILURE_RATE`
                - 실패 비율 (`0.0 ~ 1.0`)
            - `LOADTEST_PROVIDER_FAILURE_MODE`
                - 실패 유형
                - `RETRYABLE`인 경우 재시도 대상으로 분류
- **애플리케이션 설정**
    - 운영
        - HikariCP `maximum-pool-size`: `10`
    - 부하 테스트
        - 설정 파일: `loadtest/setup/test-env/server.env`
        - Spring 프로필: `prod,loadtest`
        - JVM
            - Java 25 (`amazoncorretto:25-alpine`)
            - 힙 상한 별도 지정 없음
        - 컨테이너 메모리 상한
            - Spring Boot: `1200m`
            - nginx: `64m`
            - Alloy: `300m`
        - HikariCP
            - `maximum-pool-size`: `30` (`DB_POOL_SIZE`)
            - `connection-timeout`: `5,000ms` (`DB_CONNECTION_TIMEOUT_MS`)
    - 차이
        - 운영의 HikariCP pool은 `10`, 부하 테스트는 `30`
        - DB의 최대 커넥션 수인 `30`까지 활용하면서 커넥션 한도를 실험 변수로 보기 위해 변경

## 3. 테스트 시나리오

실제 사용 흐름을 섞은 복합 workload와 특정 엔드포인트로 과도한 요청 상황을 확인하기 위한 단일 시나리오로 구성했습니다.

#### 복합 Workload

- 사용 스크립트 : `mixed-workload.js`
- 목적
    - 서비스의 전체 처리량과 병목 지점을 확인
    - 읽기와 알림 발송이 함께 발생하는 실제 사용 패턴을 재현
- 요청 비율
    - 읽기: **75%**
        - 알림 수신함 조회: **40%**
            - `GET /api/notifications?page=0&size=20`
        - 내 정보 조회: **20%**
            - `GET /api/users/my`
        - 친구 목록 조회: **20%**
            - `GET /api/friendships?page=0&size=20`
        - 사용자 검색: **10%**
            - `GET /api/users?keyword=...`
        - 받은 친구 요청 조회: **10%**
            - `GET /api/friends/requests?type=RECEIVED`
    - FCM 알림 발송: **15%**
        - `POST /api/notifications`
        - `notificationMethod: FCM`
    - SMS 알림 발송: **10%**
        - `POST /api/notifications`
        - `notificationMethod: SMS`
- SMS 테스트 조건
    - 발신자별 SMS 수신 대상을 고정
        - 수신 대상을 계속 변경하면 일일 수신자 제한에 먼저 도달해 서버 처리량 테스트가 `429` 제한 검증으로 바뀔 수 있기 때문

#### **단일 시나리오**

- 목적
    - 전체 처리량이 아니라 특정 엔드포인트와 보호 장치가 의도대로 동작하는지 검증
- 사용 스크립트
    - `one-to-many-test/user-me.js`
        - 단일 사용자가 하나의 엔드포인트에 요청을 집중시켰을 때의 동작 확인
    - `one-to-many-test/sms-send.js`
        - SMS 일일 수신자 제한이 실제로 동작하는지 확인
    - `one-to-many-test/fcm-send.js`
        - FCM 발송 경로의 요청 제한 동작 확인
    - `one-to-many-test/map-geocode.js`
        - 지도 프록시 단일 경로의 동작 및 제한 확인
- **부하 모델**
    - `precision`
        - 처리량 변화를 일정한 간격으로 비교하기 위한 테스트
        - `100 RPS`부터 시작
        - `100 RPS`씩 증가
        - 최대 `1000 RPS`
        - 각 단계 `3분` 유지
    - `breakpoint`
        - 서버가 안정적으로 처리하지 못하기 시작하는 구간을 찾기 위한 테스트
        - `30 → 60 → 100 → 150 → 225 → 300 → 400 → 600 → 800 → 1000 RPS`
        - 단계별 유지 시간 지정 가능
    - `single`
        - 특정 RPS에서의 상태를 집중적으로 관찰하기 위한 테스트
        - 지정한 RPS를 일정 시간 동안 유지
- **테스트 데이터**
    - 사용자: `1,000명`
    - 고정 친구 관계: `500건`
    - 알림: 약 `20,000건`
    - 동일한 데이터셋을 기준으로 부하 수준만 변경하여 각 테스트 결과를 비교

## 4. 실행 방법

#### **전체 실행**

- 실행 권한 부여 및 실행

    ```bash
    chmod +x loadtest/run-loadtest.sh
    ./loadtest/run-loadtest.sh
    ```

- 실행 과정
    - Cloudformation을 이용한 AWS 환경 구축
        - 키페어 생성
        - 부하 테스트 인프라 생성
        - MySQL 설치
        - 서비스 배포
    - 사전 데이터 준비
        - 테스트 fixture 생성
        - 테스트용 JWT 생성
    - 사용자 선택
        - 테스트 시나리오 선택
    - k6 를 이용한 테스트 진행
    - 결과 저장
    - 테스트 AWS 리소스 삭제

#### **반복 실행기**

- 여러 애플리케이션 이미지 후보의 성능을 동일한 조건에서 반복 비교 시 사용
- 실행 예시

    ```bash
    IMAGE_TAGS=latest,candidate-a,candidate-b \
      MYSQL_ROOT_PASSWORD='...' \
      ./loadtest/run-ai-optimization.sh
    ```

- 실행 방식
    - `IMAGE_TAGS`에 비교할 이미지 태그 지정
    - 후보마다 독립된 부하 테스트 스택 생성
    - 동일한 목표 부하 실행
    - 테스트 종료 후 결과 저장
- 결과 저장 위치
    - `docs/loadtest/300-tps/runs/<run-id>/`

#### **테스트 환경 수동 삭제**

- 실행

    ```bash
    ./loadtest/setup/teardown-loadtest.sh --yes
    ```

- 사용 시점
    - 테스트 도중 중단된 경우
    - 자동 정리가 정상적으로 수행되지 않은 경우

#### **테스트 데이터**

- `generated/seed.sql`
    - 테스트 사용자
    - 친구 관계
    - 알림 데이터
    - MySQL에 입력하기 위한 SQL
- `generated/fixture.json`
    - k6가 테스트 중 사용하는 사용자 및 관계 fixture
- `generated/tokens.json`
    - 테스트 사용자의 access token
    - `JWT_SECRET`으로 서명

## 5. 실험 결과

### 단일 엔드포인트 제한

#### A. 최초(사용자 단위 요청량 제한이 없음)

- 테스트 방식 : 같은 JWT로 `GET /api/users/my`에 200 → 300 → 400 RPS(각 1분)를 집중.
- 결과
    - HTTP 요청 수 : `47,718`건
    - 실제 처리율 : `265.06 req/s`
    - HTTP 실패율 : `2.04%`
    - 429 응답 : `0`건
    - 네트워크 오류 / EOF : `881`건
    - 5xx 응답 : `92`건
    - p90 : `1.19s`
    - p95 : `2.76s`
    - 최대 VU : `537`
- 분석
    - 서버가 초과 요청을 거절한 것이 아니라 감당하지 못해 연결을 끊음.
    - 제한이 있었다면 한도 초과 요청은 DB 대기에 들어가기 전에 `429`로 끝났어야 함.

#### B. nginx 제한 적용

- nginx 제한를 통해 악의적인 사용자의 대규모 요청을 방지하고자 하였음.
    - 정상 사용자 1인의 순간 최대 8건으로 잡고, 공유 IP 5명으로 설정하여 burst 30으로 제한.

        ```
        limit_req_zone $binary_remote_addr zone=per_ip_api:10m rate=10r/s;
        limit_req_zone $host zone=global_api:10m rate=100r/s;
        limit_conn_zone $binary_remote_addr zone=per_ip_conn:10m;
        ```

- 테스트 방식 : `user-me.js`로 같은 엔드포인트를 100 RPS로 고정 실행. 6회 실행
- 결과(1회는 기준점이라서 제외, 2 ~ 6회차)
    - 요청 수 : `1,399`건
    - 처리율 : `99.74 req/s`
    - p50 : `9.95ms`
    - p95 : `32.37ms`
    - 429 응답 : `1,229`건
    - nginx 503 : `17.5`건
    - 앱 upstream 5xx : `23.6`건
    - 네트워크 오류 : `0`건
- 분석
    - fixture 미주입으로 인한 앱 5xx 발생
        - 결과 : 3회차에서 앱 upstream 5xx `95`건 발생
        - 원인 : JWT는 생성했지만 fixture 사용자를 DB에 주입하지 않은 상태에서 테스트 실행
        - 근거 : 애플리케이션 로그에서 `USER-300(사용자를 찾을 수 없습니다)` 확인
        - 조치 : `seed.sql`을 DB 초기화 직후 실행하도록 순서 변경
        - 확인 : 5회차부터 앱 upstream 5xx `0`건
    - 이후 5xx는 nginx 503으로 분리
        - 결과 : 애플리케이션 실패와 nginx 게이트웨이 보호 동작을 구분 가능
        - 원인 : 남은 5xx가 애플리케이션 예외가 아니라 nginx에서 반환한 `503`
        - 확인 : 앱 upstream 5xx와 nginx 503을 별도 지표로 집계
    - 429는 nginx Rate Limit에 의해 발생
        - 결과 : `100 RPS` 고정 부하에서 `429` 응답 `869`건 발생
        - 원인 : 단일 IP·단일 사용자로 요청을 집중해 nginx의 IP당 `10r/s` 제한 초과
        - 해석 : 서버 처리 실패가 아니라 설정한 Rate Limit이 정상적으로 동작한 결과

#### C. SMS 중복 수신자 요청 및 `tryConsume(0)` 결함 확인

- 테스트 방식 : `POST /api/notifications`의 SMS 발송 경로에 동일 발신자·동일 수신자로 `200 → 300 → 400 RPS`를 각각 15초씩 집중.
- 결과
    - HTTP 요청 수
        - 수정 전 : `11,997`건
        - 수정 후 : `11,996`건
    - 실제 처리율
        - 수정 전 : `266.52 req/s`
        - 수정 후 : `266.56 req/s`
    - 429 응답
        - 수정 전 : `11,517`건 (`96.0%`)
        - 수정 후 : `11,516`건 (`96.0%`)
    - 5xx 응답
        - 수정 전 : `479`건 (`4.0%`)
        - 수정 후 : `157`건 (`1.3%`)
    - 정상 응답
        - 수정 전 : `1`건 (`0.01%`)
        - 수정 후 : `323`건 (`2.7%`)
    - 네트워크 오류 / EOF
        - 수정 전 : `0`건
        - 수정 후 : `0`건

        - 수정 전 : `17.69ms`
        - 수정 후 : `15.46ms`
- 분석
    - 429 응답은 SMS 일일 수신자 한도만의 결과로 볼 수 없음
        - 원인 : 단일 IP에서 `200 ~ 400 RPS`를 집중하면서 nginx의 요청 제한도 함께 동작
        - 한계 : 동일한 수신자를 반복 사용했기 때문에 신규 수신자 수를 기준으로 하는 일일 한도 자체를 검증하기에도 적합하지 않은 시나리오
        - 해석 : `11,516`건의 429를 전부 SMS 일일 수신자 제한에 의한 응답으로 해석하지 않음
        - 조치 : 이후 서버 처리량 및 애플리케이션 제한 검증에서는 부하 테스트 전용 nginx의 `limit_req`와 `limit_conn`을 제거
    - `tryConsume(0)` 호출 결함 확인
        - 원인 : 이미 예약된 수신자에게 다시 요청하면 신규 수신자 수가 `0`이지만 Bucket4j의 `tryConsume(0)`을 호출
        - 결과 : `IllegalArgumentException`이 발생하면서 일부 요청이 5xx로 응답
        - 조치 : 신규 수신자 수가 `0`이면 Bucket4j를 호출하지 않고 조기 반환하도록 수정
        - 확인 : 정상 응답 `1`건 → `323`건, 5xx `479`건 → `157`건으로 개선
        - 한계 : 당시 nginx 제한도 함께 동작하고 있었으므로 감소한 5xx 전체를 애플리케이션 수정 효과로만 해석하지 않음

#### D. 남은 5xx 원인 분리

- 테스트 방식 : `tryConsume(0)` 수정 후에도 남아 있던 5xx의 원인을 확인하기 위해 teardown 전에 SSH로 애플리케이션·nginx 로그를 직접 확인.
- 결과
    - 확인 대상 5xx : `24`건
    - 애플리케이션 500 로그 : `0`건
    - 애플리케이션 예외 스택트레이스 : `0`건
    - nginx 503 : `24`건
    - `limiting connections by zone "per_ip_conn"` : `24`건
- 분석
    - 남은 5xx는 애플리케이션 결함이 아닌 nginx 연결 제한으로 발생
        - 원인 : 단일 IP에서 요청을 집중하면서 nginx의 `limit_conn`에 도달
        - 근거 : 발생한 5xx `24`건과 nginx `503` 및 `per_ip_conn` 제한 로그 `24`건이 정확히 일치
        - 해석 : 실제 사용자는 여러 IP로 분산되지만 부하 테스트에서는 단일 IP에서 요청해 발생한 테스트 방식의 한계
        - 조치 : 이후 부하 테스트 전용 nginx에서 `limit_req`와 `limit_conn` 제거
    - `tryConsume(0)` 수정이 정상적으로 동작
        - 근거 : 신규 수신자 수가 `0`인 요청이 모두 `202`로 정상 응답
        - 해석 : 수정 이후 확인된 애플리케이션 경로에서는 조기 반환 로직이 정상 적용됨

- 테스트 방식 : 공급사 지연을 `30초`(`LOADTEST_PROVIDER_DELAY_MS=30000`)로 설정하고 SMS 발송 중 `docker kill`로 애플리케이션 컨테이너를 강제 종료.

- 분석
    - 강제 종료 이후에도 `PROCESSING` 상태의 알림이 유실되지 않음
        - 확인 : 애플리케이션 재시작 후 복구 스케줄러가 `PROCESSING` 상태로 남아 있던 알림을 전부 회수

    - 외부 공급사 호출과 DB 트랜잭션을 분리한 구조가 장애 상황에서도 동작
        - 조건 : 공급사 응답이 `30초` 지연된 상태에서 애플리케이션을 강제 종료
        - 해석 : 외부 호출 중 프로세스가 종료되더라도 긴 DB 트랜잭션에 의존하지 않고 후속 복구 가능
    - 상태 머신 기반 복구 흐름 검증
        - 흐름 : `PROCESSING` 상태 유지 → 애플리케이션 재시작 → 복구 스케줄러 탐지 → 재처리
        - 확인 : 비정상 종료 후에도 처리 중이던 알림을 다시 복구 경로로 진입시킬 수 있음을 확인
- 한계
    - 복구 스케줄러가 미완료 작업을 다시 회수하는 것까지 검증했으며, 외부 공급사에서 실제 SMS가 중복 발송되지 않는 `Exactly Once` 처리를 검증한 테스트는 아님
    - 장애 발생 시점이 공급사 요청 전·요청 중·응답 직후 등 여러 구간으로 세분화되지 않아 모든 장애 타이밍을 검증하지는 않음
    - 단일 애플리케이션 컨테이너를 강제 종료한 시나리오로, EC2 자체 장애·DB 장애·네트워크 단절과 같은 인프라 장애는 포함하지 않음
    - 복구 완료 시간, 재처리 횟수, 중복 처리 여부 등의 정량 지표를 별도로 측정하지 않음

## 8. TPS 165까지만 확인한 후 그 이상을 확인하지 않는 이유.

- `1` 에서 명시한 것처럼 현재는 사용자가 없고, 가정적인 환경임.
- 서비스 특성 상 사용자 1명이 발생하는 트래픽은 낮고, 추정치를 보기 위해서임.
- 과도하게 트래픽이 발생한 실험에서는 약 110 TPS 에서 처리가 힘든 것을 확인 함.

- `피크 시간 RPS` = `DAU` × `피크 집중률` × `사용자 1명의 1회 흐름 요청 수` ÷ `3,600`
    - 가정 : 피크 집중률 40% (18~19시 1시간에 집중), 1회 흐름 = 6건
    - 피크 RPS ≈ DAU ÷ 1,500
- 예상 처리 가능한 사용자 수.

    | DAU | 피크 1시간 요청 수 | 평균 피크 RPS | 검증된 165 req/s 대비 |
    | --- | --- | --- | --- |
    | 10,000 | 24,000 | 6.7 | 4% |
    | **60,000** | 144,000 | **40.0** | **24%** |
    | 100,000 | 240,000 | 66.7 | 40% |
