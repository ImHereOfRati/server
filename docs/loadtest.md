# 부하 테스트와 성능 검증 — 실제로 어디까지 버티는가

이 문서는 ImHere 서버의 **처리량 한계를 어떻게 측정했고, 병목이 무엇이었으며, 무엇을 고쳤고, 무엇이 아직 확정되지 않았는지**를 기록합니다. 지금까지 실행한 부하 테스트 결과를 전부 담았습니다.

세 문서가 역할을 나눠 갖고 있습니다.

| 문서                                           | 답하는 질문                         |
|----------------------------------------------|--------------------------------|
| [서버 아키텍처](imhere-architecture.md)            | 왜 이렇게 설계했는가 (구조·설계 판단)         |
| [배포와 운영](imhere-deployment-and-operation.md) | 실제로 어떻게 배포하고 장애를 막았는가 (운영·인프라) |
| **이 문서**                                     | 그 설계가 실제 부하에서 버티는가 (측정·병목·개선)  |

**실행 명령과 환경 변수 전체 목록은 [`loadtest/README.md`](../loadtest/README.md)에 있습니다.** 여기서는 측정의 목적·조건·결과·해석을 다룹니다.

---

## 1. 무엇을 왜 측정했나

- ImHere는 위치가 바뀌는 순간에만 요청이 발생하므로 평상시 지속 트래픽은 크지 않음.
- 그럼에도 측정이 필요한 이유
    - 출퇴근 시간대처럼 이동이 몰리는 구간이 있음.
    - 네트워크가 끊겼다 붙으면 앱이 재시도함.
    - 같은 토큰으로 API를 반복 호출하는 악의적 사용이 가능함.
    - 외부 공급사가 복구될 때 밀린 알림이 한꺼번에 나감.
- 알고 싶은 것
    1. 안정적으로 처리하는 구간은 어디까지인가
    2. 한계에 닿았을 때 **무엇이 먼저 무너지는가** (CPU? DB? 커넥션?)
    3. 보호 장치(속도 제한)와 복구 장치가 **실제로 동작하는가**

> 이 측정값은 `t3.small` 1대 + MySQL 1대 구성의 값입니다. "이 서비스가 감당 가능한 사용자 수"가 아니라 **"지금 이 구성의 한계"**로 읽어야 합니다.

## 2. 왜 전용 환경을 따로 만들었나

- 운영 환경에 부하를 걸 수 없음.
- 로컬 PC에서 앱을 띄워 측정하면 그 숫자는 운영과 무관함. CPU·메모리·디스크·네트워크가 다르고, DB가 같은 기계 안에 있어 네트워크 왕복 비용이 사라짐.
- 그래서 이렇게 설계
    - **운영과 같은 사양·같은 이미지** — `t3.small`에서, CD가 ECR에 올린 그 이미지를 pull해서 사용. 로컬 빌드를 쓰지 않음.
    - **운영과 완전히 분리** — 별도 VPC, 별도 스택.
    - **쓰고 버림** — 테스트 종료 시 CloudFormation 스택을 통째로 삭제. 중단해도 종료 트랩이 teardown 시도.
    - **부하 발생기는 로컬 PC** — k6 전용 EC2를 만들지 않음.

## 3. 측정 환경

기본 리전은 `ap-northeast-2`, 템플릿은 [
`load-test-aws-setup.yaml`](../loadtest/setup/infra/cloudformation/load-test-aws-setup.yaml)입니다.

```text
로컬 PC
  └─ k6 ── HTTP/HTTPS ──▶ 애플리케이션 EC2  (t3.small)
                            ├─ Spring Boot
                            ├─ nginx
                            └─ Alloy ──────▶ 모니터링 EC2  (t3.small)
                                              ├─ Prometheus
                                              ├─ Loki
                                              ├─ Tempo
                                              └─ Grafana
                                  │
                                  ▼
                            데이터베이스 EC2  (t3.small)
                              └─ MySQL 8.0 (OS에 직접 설치)
```

### 서버

| 항목           | 값                                                                                  |
|--------------|------------------------------------------------------------------------------------|
| 애플리케이션 EC2   | Amazon Linux 2023, `t3.small` (2 vCPU / 2 GiB) — Spring Boot + nginx + Alloy 동시 실행 |
| 데이터베이스 EC2   | Amazon Linux 2023, `t3.small` — MySQL Community Server 8.0을 Docker가 아니라 OS에 직접 설치  |
| 모니터링 EC2     | Amazon Linux 2023, `t3.small` — Grafana + Prometheus + Loki + Tempo                |
| VPC / Subnet | `10.51.0.0/16` / `10.51.1.0/24` (운영의 `10.50.x`와 겹치지 않음)                            |

### 애플리케이션 설정 (`loadtest/setup/test-env/server.env`)

| 항목                            | 값                                                               |
|-------------------------------|-----------------------------------------------------------------|
| Spring 프로필                    | `prod,loadtest`                                                 |
| JVM                           | Java 25 (amazoncorretto:25-alpine), 힙 상한 별도 지정 없음               |
| 컨테이너 메모리 상한                   | 앱 1200m / nginx 64m / alloy 300m                                |
| HikariCP `maximum-pool-size`  | **30** (`DB_POOL_SIZE`)                                         |
| HikariCP `connection-timeout` | **5,000ms** (`DB_CONNECTION_TIMEOUT_MS`)                        |
| MySQL `max_connections`       | **30**                                                          |
| 외부 공급사                        | 가짜 Adapter (`LOADTEST_PROVIDER_DELAY_MS=0`, `FAILURE_RATE=0.0`) |

### 부하 발생기

| 항목    | 값                                                    |
|-------|------------------------------------------------------|
| 위치    | 로컬 PC (AWS 밖), 공인 IP `/32`만 보안 그룹에 허용                |
| 도구    | k6, `ramping-arrival-rate` executor                  |
| VU 설정 | `preAllocatedVUs` 기본 300, `maxVUs` 기본 2000 (실행별로 조정) |

> **기록해 두는 한계** — 부하 발생기 PC의 CPU·메모리·네트워크 대역폭을 기록하지 않았고, 부하 발생기 자체가 병목이 아니었음을 별도로 검증하지 않았습니다.

### 운영과 무엇이 다른가

측정값을 해석할 때 먼저 봐야 하는 표입니다. **"운영에서도 이 숫자가 나온다"고 바로 말할 수 없는 지점**들입니다.

| 항목            | 운영                                                | 부하 테스트                              | 왜 다르게 뒀나                              |
|---------------|---------------------------------------------------|-------------------------------------|---------------------------------------|
| nginx 속도 제한   | `limit_req` 10r/s(IP)·100r/s(전체), `limit_conn` 20 | **전부 제거**                           | 제한을 둔 채로는 서버가 아니라 nginx의 한계를 측정하게 됨   |
| HikariCP pool | 10 (`DB_POOL_SIZE` 기본값)                           | 30                                  | 커넥션 한도를 실험 변수로 다루기 위해                 |
| TLS / 도메인     | Let's Encrypt, 실제 도메인                             | self-signed, `server_name _`        | 임시 환경에 도메인을 붙일 수 없음                   |
| MySQL         | 외부 호스팅                                            | DB EC2에 직접 설치, `max_connections=30` | "네트워크 건너편 DB" 조건은 같게, 커넥션 한도는 실험 변수로  |
| FCM / SMS     | 실제 Firebase · Solapi                              | `loadtest` 프로필의 가짜 Adapter          | 공급사 요금·외부 제한에 막히지 않고 서버 자신의 한계를 재기 위해 |
| 관측 백엔드        | Grafana Cloud                                     | 모니터링 EC2에 직접                        | 짧고 굵은 대량 메트릭이 SaaS 수집 한도·요금에 바로 걸림    |

가짜 Adapter는 성공만 돌려주지 않고 지연·실패를 흉내 낼 수 있습니다.

| 환경 변수                            | 뜻                                |
|----------------------------------|----------------------------------|
| `LOADTEST_PROVIDER_DELAY_MS`     | 공급사 호출에 걸리는 시간(ms)               |
| `LOADTEST_PROVIDER_FAILURE_RATE` | 실패 비율 (0.0 ~ 1.0)                |
| `LOADTEST_PROVIDER_FAILURE_MODE` | 실패 유형. `RETRYABLE`이면 재시도 대상으로 분류 |

## 4. 테스트 시나리오

단일 엔드포인트만 때린 숫자는 서비스 처리량이 아닙니다. 두 종류를 나눠 씁니다.

### 복합 workload (`mixed-workload.js`) — 처리량 판단용

| 종류        |      비율 | 엔드포인트                                                 |
|-----------|--------:|-------------------------------------------------------|
| 읽기        | **75%** | 아래 표 참고                                               |
| FCM 알림 발송 | **15%** | `POST /api/notifications` (`notificationMethod: FCM`) |
| SMS 알림 발송 | **10%** | `POST /api/notifications` (`notificationMethod: SMS`) |

| 읽기 엔드포인트                                      | 읽기 중 비율 |
|-----------------------------------------------|--------:|
| `GET /api/notifications?page=0&size=20` (수신함) |     40% |
| `GET /api/users/my`                           |     20% |
| `GET /api/friendships?page=0&size=20`         |     20% |
| `GET /api/users?keyword=...` (검색)             |     10% |
| `GET /api/friends/requests?type=RECEIVED`     |     10% |

- SMS 대상은 발신자마다 고정. 그러지 않으면 일일 수신자 한도가 걸려 처리량 테스트가 429 테스트로 변함.

### 단일 시나리오 — 보호 장치 검증용

| 스크립트                              | 목적                              |
|-----------------------------------|---------------------------------|
| `one-to-many-test/user-me.js`     | 단일 사용자가 한 엔드포인트에 요청을 집중시킬 때의 거동 |
| `one-to-many-test/sms-send.js`    | SMS 일일 수신자 한도가 실제로 작동하는지        |
| `one-to-many-test/fcm-send.js`    | FCM 경로에서의 제한 동작                 |
| `one-to-many-test/map-geocode.js` | 지도 프록시 단일 경로                    |

### 부하 모델

| 계획           | 형태                                                                     |
|--------------|------------------------------------------------------------------------|
| `precision`  | 100 RPS에서 시작해 100씩 올려 1000까지, 각 3분                                     |
| `breakpoint` | 30 → 60 → 100 → 150 → 225 → 300 → 400 → 600 → 800 → 1000 (단계 시간 지정 가능) |
| `single`     | 지정한 RPS 한 단계만 지정 시간 동안                                                 |

측정 데이터는 사용자 1,000명, 고정 친구 관계 500건, 알림 약 20,000건입니다.

### 사용자 1명의 흐름에는 몇 번의 요청이 필요한가

현재 [`mixed-workload.js`](../loadtest/k6/test/many-people-many-request-test/mixed-workload.js)는 **반복 1회(iteration)에 HTTP 요청 1건**을 보냅니다. 응답 뒤 기본 50ms를 쉬고, 다음 반복에서 계정을 다시 선택합니다. 따라서 VU 1개는 한 명의 고정된 사용자가 아니며, fixture 1,000명도 동시 사용자 1,000명을 검증했다는 뜻은 아닙니다. 여기서 TPS는 DB 트랜잭션 수가 아니라 HTTP 요청 수입니다.

사용자 수를 계산하기 위해 다음과 같은 **예시 이용 흐름 1회 = 6건**을 정의할 수 있습니다. 실제 앱의 호출 로그로 확정한 여정이 아니라, 서버에 존재하는 API를 조합한 산정용 가정입니다.

| 사용자 행동 | 요청 | 건수 |
|---|---|---:|
| 로그인된 상태에서 앱 진입·목록 확인 | 내 정보, 친구 목록, 받은 친구 요청, 알림 수신함 각각 조회 | 4 |
| 한 대상에게 도착 알림 요청 | `POST /api/notifications` — FCM 또는 SMS 중 하나 | 1 |
| 알림 수신함 갱신 | `GET /api/notifications?page=0&size=20` | 1 |
| **흐름 1회 합계** | **조회 5건 + 알림 요청 1건** | **6** |

이미 초기 정보를 읽어 둔 사용자가 도착 알림만 보내면 **1건**, 친구 검색까지 하면 위 흐름에 **1건 추가해 7건**입니다. 로그인·토큰 갱신·지도 조회·페이지 추가 조회·재시도는 위 6건에 포함하지 않았으며, 발생할 때마다 더해야 합니다. FCM과 SMS를 각각 요청하면 발송 요청도 2건입니다.

알림 API의 `202`는 발송 **접수**를 뜻합니다. 그 뒤 실행되는 이벤트 저장, DB 커밋, 외부 공급사 호출은 클라이언트 HTTP 요청 수에 더하지 않지만 서버 자원을 사용합니다. 수신자 수와 재시도가 늘면 같은 HTTP TPS에서도 부하는 커집니다.

### TPS를 동시에 활동하는 사용자 수로 환산하면

사용자 수는 **한 사람이 얼마나 자주 요청하는가**에 따라 달라집니다. 다음 식에서 T는 대기 시간을 포함해 같은 사용자가 흐름을 반복하는 주기입니다.

```text
C = 사용할 수 있는 HTTP 처리량(req/s)
q = 사용자 1명이 흐름 1회에 보내는 요청 수
T = 같은 사용자의 흐름 반복 주기(초)

사용자 1명당 평균 요청률 = q / T
동시 활성 사용자 수 환산값 N = floor(C × T / q)
```

**C = 165 req/s가 지속 가능하다고 가정**하면 다음과 같습니다. 요청이 시간에 고르게 분산되고, 요청당 비용이 측정한 혼합 부하와 유사하다는 조건입니다.

| 이용 패턴 | 요청 수 q | 반복 주기 T | 사용자당 평균 요청률 | 165 req/s 기준 환산 인원 |
|---|---:|---:|---:|---:|
| 도착 알림만 분당 1회 | 1 | 60초 | 약 0.0167 req/s | 9,900명 |
| 6건 흐름을 10초마다 반복 | 6 | 10초 | 0.6 req/s | 275명 |
| 6건 흐름을 30초마다 반복 | 6 | 30초 | 0.2 req/s | 825명 |
| 6건 흐름을 분당 1회 반복 | 6 | 60초 | 0.1 req/s | 1,650명 |
| 6건 흐름을 5분마다 반복 | 6 | 300초 | 0.02 req/s | 8,250명 |

예를 들어 **분당 6건씩 보내는 사용자 1,650명**은 합계 9,900건/분, 즉 평균 165 req/s입니다. 이는 그 인원이 같은 시간대에 활동하면서 요청을 나눠 보내는 경우입니다. 1,650명이 같은 1초 안에 6건을 모두 보내면 9,900 req/s가 되어 전혀 다른 부하가 됩니다. 165 req/s를 6건 흐름으로 나누면 약 **27.5개의 흐름/초에 해당하는 요청 예산**이며, 모든 흐름이 1초 안에 완료된다는 보장은 아닙니다.

**현재 검증된 최대 동시 사용자 수는 아직 없습니다.** 165 req/s는 6.2절의 30→300 ramp-up 실행에서 얻은 전체 평균이며, 6.3절에는 165 TPS 단일 실행에서도 실패한 기록이 있습니다. 앞선 대화에서 이를 "165 TPS 안정 상한"으로 단정한 해석은 정정합니다. 위 인원은 용량 산정을 위한 조건부 계산값이고, 장시간 지속 가능한 사용자 수를 검증한 결과가 아닙니다.

또한 6건 예시 흐름은 조회 5/6·발송 1/6이므로 기존 혼합 부하(조회 75%·발송 25%)와 구성이 다릅니다. 특히 알림만 보내는 첫 번째 행은 기존 혼합 TPS를 그대로 적용하기 어렵습니다. 실제 사용자 흐름과 반복 주기를 측정한 뒤 같은 비율로 재검증해야 합니다. 운영 여유를 30% 두겠다는 가정을 추가하면 분당 6건 기준 환산 인원은 `floor(165 × 0.7 × 60 / 6) = 1,155명`이지만, 이것도 보장 수치는 아닙니다.

여기서 말하는 동시 활성 사용자와 **응답을 기다리는 동시 요청 수**도 구분해야 합니다. 안정 상태의 평균 동시 요청 수는 대략 `요청률 × 평균 응답 시간(초)`입니다. 평균 응답 시간이 29.15ms인 실행에 164.90 req/s를 적용하면 약 4.8건입니다. 이 값은 사용자 수나 DB 연결 수가 아니며, 계산에 p95/p99를 평균 대신 넣어서는 안 됩니다.

### 하루 평균 1회 사용하고, 대상 2명에게 알림을 보내는 경우

앞의 예시 흐름처럼 앱 진입·목록 조회 4건과 수신함 갱신 1건을 한다고 가정합니다. 두 대상에게 같은 채널(FCM 또는 SMS)로 보내면 `targetIds`에 두 대상을 담아 **HTTP 요청 1건**으로 접수할 수 있습니다. 서버는 `NotificationEvent.from()`에서 대상별 이벤트를 만들므로 **대상 알림은 2건**입니다. 서로 다른 채널로 보내거나 대상을 따로 요청하면 발송 HTTP 요청은 2건이 됩니다.

| 하루 1회 이용 방식 | 사용자당 HTTP 요청/일 | 대상 알림/일 | 165 req/s를 24시간 균등 사용한다고 가정한 DAU 환산 |
|---|---:|---:|---:|
| 조회 5건 + 두 대상을 묶은 발송 요청 1건 | 6 | 2 | 2,376,000명 |
| 조회 5건 + 대상별 발송 요청 2건 | 7 | 2 | 2,036,571명 |
| 조회 없이 두 대상을 묶은 발송 요청만 수행 | 1 | 2 | 14,256,000명 |

계산식은 `일일 활성 사용자(DAU) 환산 = floor(165 × 86,400 / 사용자당 HTTP 요청 수)`입니다. **이 표는 HTTP 요청 예산을 일일 이용자 수로 나눈 산술값이며, 실제 수용 가능한 최대 DAU나 동시 접속자 수를 뜻하지 않습니다.** 하루 한 번 이용하는 사람이 하루 종일 요청을 보내지는 않으므로, 여기서는 앞의 동시 활성 사용자 대신 DAU로 해석해야 합니다.

예를 들어 기본 흐름(6건)으로 **DAU 10,000명**이 이용하면 하루 HTTP 요청은 **60,000건**, 대상 알림은 **20,000건**입니다. 24시간 균등 분산 시 평균 **약 0.69 req/s**, 같은 사용량이 1시간에 고르게 집중되면 **약 16.67 req/s**, 10분에 집중되면 **100 req/s**가 됩니다. 따라서 일평균 이용 횟수와 함께 출퇴근 등 피크 시간의 집중도를 봐야 합니다.

대상 2명에 대한 발송은 HTTP 1건으로 묶어도 대상별 이벤트 처리와 공급사 발송이 필요합니다. 기존 실험은 발송 요청당 대상 1명이었으므로 위 계산은 늘어난 비동기 작업량을 검증하지 않습니다. 실제 DAU 상한을 정하려면 이 2명 발송 흐름으로 HTTP 오류율·지연시간과 알림 완료 속도·backlog를 함께 측정해야 합니다. 앞서 설명한 대로 **165 req/s 자체도 확정된 지속 처리 한계는 아닙니다.**

실행 직후 DB에서 수집한 스냅샷입니다.

### 증거 1 — DB 커넥션이 항상 한도에 붙어 있다

| 실행                  | `Max_used_connections` | `Threads_connected` | `Threads_running` | `Innodb_row_lock_waits` |
|---------------------|-----------------------:|--------------------:|------------------:|------------------------:|
| 6.2-2 (기준선)         |                     31 |                  29 |                 2 |                      20 |
| 6.2-4 (VU 300)      |                     31 |                  31 |                 2 |                      19 |
| 6.2-5 (Slice)       |                     31 |                  30 |                 2 |                      10 |
| 6.3-6 (steady 300)  |                     31 |                  30 |                 2 |                       0 |
| 6.3-8 (195 TPS)     |                     31 |                  28 |                 2 |                       1 |
| 6.3-11 (breakpoint) |                     31 |                  31 |                 2 |                       1 |

- `max_connections = 30`인데 매 실행 커넥션이 전부 점유됩니다.
- 반면 `Threads_running`은 항상 **2**입니다. **연결은 꽉 찼는데 실제로 CPU를 쓰는 쿼리는 거의 없습니다.** 커넥션이 연산이 아니라 대기와 커밋에 묶여 있다는 뜻입니다.
- 락 경합도 병목이 아닙니다(`Innodb_row_lock_waits` 0~20).

### 증거 2 — 시간의 대부분을 `COMMIT`이 먹는다

6.2-5 실행(10분)의 상위 statement digest입니다. 원본 `sql-optimizer.md`의 `avg_ms` 열은 실제로는 **마이크로초**이므로, 아래 평균은 `총 시간 ÷ 호출 수`로 다시
계산했습니다.

| statement                                                                                       |    호출 수 |        총 시간 |     평균 |
|-------------------------------------------------------------------------------------------------|--------:|------------:|-------:|
| `COMMIT`                                                                                        | 383,925 | 1,170,682ms | 3.05ms |
| `SET autocommit = ?`                                                                            | 768,392 |    33,359ms | 0.04ms |
| `UPDATE notification SET ... WHERE id = ?`                                                      |  38,729 |    14,708ms | 0.38ms |
| `SELECT ... FROM notification WHERE id = ?`                                                     |  77,449 |    14,403ms | 0.19ms |
| `UPDATE notification SET status = ? WHERE id = ? AND status IN (...)`                           |  38,697 |    13,758ms | 0.36ms |
| `INSERT INTO notification (...)`                                                                |  38,727 |    11,250ms | 0.29ms |
| `SELECT ... FROM notification WHERE target_identifier = ? ... ORDER BY created_at DESC LIMIT ?` |  19,740 |    10,163ms | 0.51ms |
| `UPDATE event_publication SET status = ? WHERE id = ? AND status != ?`                          |  38,725 |    10,018ms | 0.26ms |
| `INSERT INTO event_publication (...)`                                                           |  39,219 |     8,615ms | 0.22ms |
| `DELETE FROM event_publication WHERE id = ?`                                                    |  38,718 |     8,099ms | 0.21ms |

- 개별 쿼리는 **전부 1ms 미만**입니다. 느린 쿼리 때문에 막힌 게 아닙니다. 문제는 **횟수**입니다.

```text
10분 동안
  HTTP 요청       98,998건
  COMMIT         383,925회
                 → 요청 1건당 평균 약 3.9회 커밋
```

- 알림 한 건이 `notification` INSERT → `event_publication` INSERT → 상태 UPDATE ×2 → `event_publication` DELETE로 이어지고, 각 단계가 짧은
  트랜잭션으로 쪼개져 있기 때문입니다.
- 커넥션 풀이 30인데 초당 수백 번 커밋하면, 커넥션 하나가 잡힐 때마다 디스크 flush를 기다리는 구조가 됩니다.

### 증거 3 — 이벤트 backlog가 남는다

| 실행                  | `SENT` | 미처리 `event_publication` |
|---------------------|-------:|------------------------:|
| 6.2-2 (기준선)         | 44,548 |                   6,780 |
| 6.2-5 (Slice)       | 58,743 |                     501 |
| 6.3-6 (steady 300)  | 21,179 |                  14,299 |
| 6.3-11 (breakpoint) | 20,636 |                   3,648 |

- 부하가 클수록 미처리분이 커집니다. **생성 속도가 소비 속도를 앞지릅니다.**
- 이 잔여분이 다음 실행의 출발 조건을 오염시켰을 가능성이 6.3의 미확정 사유입니다.

### 결론

```text
CPU            → 포화 아님 (Threads_running 항상 2)
느린 쿼리       → 없음 (개별 쿼리 전부 1ms 미만)
락 경합         → 미미 (row lock waits 0~20)
DB 커넥션       → 매 실행 30/30 점유
커밋 횟수       → 요청 1건당 약 3.9회
이벤트 backlog  → 종료 후에도 수천 건 잔존
```

**병목은 애플리케이션 연산도, 특정 느린 쿼리도 아니라 "요청 한 건이 만들어 내는 쓰기 트랜잭션 수"입니다.** 이것은 브로커 없이 Modulith 이벤트를 DB에 기록하는 설계의 직접적인 대가입니다. 브로커
운영 비용을 치르지 않은 대신, 이벤트 하나하나가 DB 쓰기가 됐습니다.

### 다음에 시도할 후보

1. `event_publication` 완료 처리 방식 조정 — `completion-mode`와 삭제 시점을 바꿔 쓰기 횟수를 줄인다.
2. 알림 상태 전이 병합 — `PENDING → PROCESSING → SENT`를 매번 별도 트랜잭션으로 쓰지 않고 묶을 수 있는 구간을 찾는다.
3. MySQL `max_connections`와 Hikari pool을 분리해 측정 — 지금은 둘 다 30이라 어느 쪽 한도인지 구분되지 않는다.
4. 실행 사이 backlog 초기화를 절차로 고정한 뒤, 100 → 300 TPS를 충분한 단계 시간으로 재측정한다.
5. 부하 발생기 자체의 한계 검증 — 두 대에서 동시에 쏴 보고 처리율이 변하는지 확인한다.

실험 규칙은 [`plan.md`](loadtest/300-tps/plan.md)에 고정돼 있습니다. **후보 하나당 원인 하나만** 바꾸고, 같은 seed로 DB를 재초기화한 뒤 `ANALYZE TABLE`을
돌리고, Markdown 보고서가 없는 실행은 성공으로 인정하지 않습니다.

## 10. 지금까지 확정된 것과 확정되지 않은 것

**확정**

1. 사용자 단위 제한이 없으면 단일 사용자의 집중 요청으로 서버가 EOF를 내며 무너진다. (08-30)
2. nginx + Bucket4j 2계층 제한을 넣으면 같은 부하에서 요청의 95~96%가 `429`로 거절되고 네트워크 오류가 0이 된다. (09-03/04, FCM·SMS 모두)
3. 5xx의 출처를 애플리케이션과 게이트웨이로 분리할 수 있다. 잔여 5xx는 nginx `limit_conn`이었다. (09-04, 로그 확증)
4. 앱 컨테이너를 강제 종료해도 `PROCESSING` 알림이 복구 스케줄러로 회수된다. (09-04)
5. `t3.small` 1대 + MySQL(`max_connections=30`) 구성에서 **복합 workload 300 TPS는 처리하지 못한다.** (09-15)
6. 병목은 CPU도 느린 쿼리도 아니라 **요청당 커밋 횟수와 DB 커넥션 점유**다. (09-15 SQL 스냅샷)

**미확정**

1. **안정 처리 구간의 정확한 값.** 08-29는 100~136 RPS를 안정으로 봤지만, 09-15 후반 실행은 165~195 TPS에서도 실패율이 46~64%였습니다. 실행 간 backlog 초기화와 충분한
   단계 시간을 확보해 재측정해야 합니다.
2. **부하 발생기가 병목이 아니었는지.** 검증하지 않았습니다.
3. **`Slice` 후보의 효과.** 1회 실행만으로는 회귀와 편차를 구분할 수 없습니다.
4. **운영 설정(Hikari pool 10, nginx 제한 활성)에서의 수치.** 지금까지 측정은 전부 pool 30·제한 제거 환경입니다.

## 11. 실행 방법

```bash
chmod +x loadtest/run-loadtest.sh
./loadtest/run-loadtest.sh
```

키페어 생성 → 인프라 생성 → MySQL 설치 → 서비스 배포 → fixture·JWT 생성 → 테스트 선택 → k6 실행 → 결과 저장 → **리소스 삭제**까지 한 번에 진행합니다.

```bash
./loadtest/setup/teardown-loadtest.sh --yes
```

## 13. 안전 수칙

- **테스트 종료 후 CloudFormation 스택이 실제로 삭제됐는지 확인.** teardown이 실패하면 EC2 세 대가 계속 과금됩니다.
- `BASE_URL`을 잘못 지정하면 의도하지 않은 서버에 부하가 갑니다. 운영 도메인을 넣지 마세요.
- `LOAD_GENERATOR_CIDR`과 `OBSERVABILITY_ADMIN_CIDR`은 필요한 IP만 허용. 공인 IP가 바뀌면 기존 환경에 접속할 수 없습니다.
- `loadtest/setup/test-env/`의 값은 전부 테스트용 가짜입니다. 운영 credential을 복사하지 마세요.
- 특정 배포본을 검증하려면 `latest` 대신 명시적인 `IMAGE_TAG`를 사용. `latest`는 CD가 계속 갱신합니다.
- 연속 실행 시 **이전 실행의 backlog가 다음 실행에 섞입니다.** 실행 사이에 DB를 재초기화하고 backlog 해소를 확인해야 합니다(6.3의 미확정 사유).

## 용어 풀이

| 용어                            | 뜻                                                                                     |
|-------------------------------|---------------------------------------------------------------------------------------|
| **k6**                        | JavaScript로 시나리오를 쓰는 부하 테스트 도구입니다.                                                    |
| **TPS / RPS**                 | 초당 처리(요청) 건수. 이 문서에서는 같은 뜻으로 씁니다.                                                     |
| **VU (Virtual User)**         | k6가 만드는 가상 사용자. 동시에 요청을 보내는 흐름 하나입니다.                                                 |
| **arrival rate executor**     | "VU를 몇 명 둘까"가 아니라 "초당 몇 건을 보낼까"를 기준으로 부하를 만드는 방식. 목표를 못 맞추면 VU를 늘리거나 iteration을 버립니다. |
| **램프업 / 정상 상태**               | 부하를 서서히 올리는 구간과, 목표 부하를 계속 유지하는 구간. 램프업 구간의 평균은 목표값보다 낮게 나옵니다.                        |
| **p95 / p99**                 | 응답 시간을 줄 세웠을 때 95% / 99% 지점의 값. 평균보다 "느린 사용자의 체감"을 잘 보여 줍니다.                          |
| **EOF / 네트워크 오류**             | 응답을 받기 전에 연결이 끊긴 경우. 서버가 응답 코드조차 주지 못한 상태입니다.                                         |
| **dropped iteration**         | k6가 목표 도착률을 맞추지 못해 아예 보내지 못한 요청입니다.                                                   |
| **fixture / seed**            | 테스트를 위해 미리 만들어 넣는 사용자·데이터입니다.                                                         |
| **breakpoint 테스트**            | 부하를 계속 올려 어디서 무너지는지 찾는 방식입니다.                                                         |
| **카오스 테스트**                   | 일부러 컨테이너를 죽이는 등 장애를 주입해 복구 동작을 확인하는 방식입니다.                                            |
| **Hikari pool / pending**     | Spring Boot의 DB 커넥션 풀. pending은 커넥션을 못 받고 대기 중인 요청 수입니다.                              |
| **performance_schema digest** | MySQL이 쿼리를 형태별로 묶어 집계한 통계입니다.                                                         |
| **COMMIT 비용**                 | 트랜잭션을 확정할 때 디스크에 로그를 쓰고 기다리는 비용. 쿼리가 빨라도 커밋이 잦으면 여기서 막힙니다.                            |
| **backlog**                   | 아직 처리되지 않고 쌓여 있는 작업. 여기서는 미처리 `event_publication` 행입니다.                               |
| **quick gate**                | 본 실험 전에 짧게 돌려 명백히 나쁜 후보를 걸러 내는 예선입니다.                                                 |
| **worktree**                  | 같은 Git 저장소를 여러 디렉터리에 동시에 체크아웃하는 기능. 후보별 빌드를 섞이지 않게 합니다.                               |
