# 1인 집중 요청 Rate Limit 검증 보고서

## 요약

단일 사용자의 JWT를 모든 요청에 사용해 200→300→400 RPS로 부하를 증가시켰다.
결과에서 `429 Too Many Requests`는 관측되지 않았고, 서버가 요청을 제한하기 전에
EOF·네트워크 오류와 5xx를 발생시켰다. 따라서 현재 일반 API에는 사용자별 rate
limit이 적용되어 있지 않거나, 이 엔드포인트에 적용되지 않는 것으로 판단한다.

## 테스트 정보

| 항목 | 값 |
|---|---|
| 결과 파일 | `loadtest/generated/results/only-one-precision-20260830-172606.json` |
| 테스트 스크립트 | `loadtest/k6/imhere-only-one.js` |
| 요청 엔드포인트 | `GET /api/users/my` |
| 인증 사용자 | fixture 사용자 1명 (`ACTOR_INDEX=0`) |
| 부하 모델 | 200 → 300 → 400 RPS, 각 1분 |
| iteration당 요청 수 | 1개 |
| 테스트 대상 | AWS 격리 부하테스트 인프라, 로컬 빌드 jar |

이번 시나리오는 iteration마다 요청을 1개만 보내므로 k6의 iteration rate와 HTTP
request rate를 동일한 의미로 비교할 수 있다.

## 결과

| 지표 | 결과 |
|---|---:|
| HTTP 요청 수 | 47,718 |
| 실제 HTTP 요청률 | 265.06 req/s |
| iteration 수 | 47,718 |
| dropped iteration | 280 (1.56/s) |
| HTTP 실패율 | 2.04% |
| 네트워크 오류/EOF | 881 |
| 5xx 응답 | 92 |
| 429 응답 | 0건 관측 |
| 평균 응답시간 | 359.10ms |
| 중앙값 응답시간 | 27.70ms |
| p90 응답시간 | 1.19s |
| p95 응답시간 | 2.76s |
| 최대 응답시간 | 6.00s |
| 최대 VU | 537 |

정상 응답을 받은 요청을 기준으로 한 k6 check 성공률은 98.15%였다. 그러나
rate-limit 검증 관점에서는 요청을 정상 처리했는지가 아니라 초과 요청을 `429`로
빠르게 거절했는지가 핵심이다.

## 판정

### 사용자별 rate limit

판정: **미적용 또는 검증 불가 수준**

동일한 JWT로 요청을 집중시켰지만 rate-limit rejection metric이 생성되지 않았고,
`429` 응답도 관측되지 않았다. 반면 요청은 다음과 같이 실패했다.

```text
과도한 요청
  → 사용자별 429 차단 없음
  → 서버/네트워크 처리 지속
  → EOF 881건, 5xx 92건
```

이는 rate limit이 요청을 제어한 결과가 아니라, 서버가 감당하지 못해 연결을
종료한 결과다.

### 서버 보호 효과

판정: **보호되지 않음**

HTTP 실패율은 2.04%였고 p95 응답시간은 2.76초까지 증가했다. rate limit이
있었다면 설정된 한도를 넘은 요청은 서버 내부 작업이나 DB 대기에 들어가기 전에
`429`로 종료되어야 한다.

## 해석상의 제한

- 결과 JSON에는 단계별 RPS·상태코드별 응답 수가 별도 저장되지 않아 200/300/400
  RPS 각각의 정확한 오류율은 분리할 수 없다.
- `only_one_rate_limit_count`가 0인 경우 k6 summary에 metric 자체가 생략될 수
  있으므로, 다음 실행에서는 429 수를 항상 기록하도록 metric 초기화 또는
  상태코드별 Counter를 보강하는 것이 좋다.
- 이 결과는 사용자별 rate limit 부재를 검증하지만, 여러 사용자에게 분산된
  global concurrency limit의 존재 여부까지 검증하지는 않는다.

## 권장 후속 검증

1. 사용자별 rate limit을 적용한다.
2. 동일 테스트를 재실행해 `429`가 발생하는지 확인한다.
3. `429` 발생 중 `5xx`, EOF, dropped iteration이 낮게 유지되는지 확인한다.
4. 별도 distributed 시나리오로 1,000명 사용자에게 200~400 RPS를 분산해
   전체 자원 보호 여부를 검증한다.

성공 판정의 예시는 다음과 같다.

```text
429 발생: 예
5xx/EOF: 허용 기준 이하
p95: 서비스 SLO 이하
앱 컨테이너: 재시작 없음
DB connection pending: 지속 증가 없음
```
